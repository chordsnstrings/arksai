# ArksAI — Feature List

A self-hosted, Claude-Code-style web coding agent for **non-technical teams**: describe
something once → get one finished thing that looks perfect, works perfectly, and is
actually live/usable. Powered by MiniMax (the LLM brain + image/vision/speech/video), with Suno for music.

> **Maintenance:** keep this file current — every shipped change that adds, removes, or
> meaningfully alters a feature should update this list in the same commit.
> _Last updated: 2026-06-24._

## Robots — the agentic surface
- A **separate, full-page workspace for standing agents**, reached from a **"🤖 Robots"** link in the sidebar and linkable at **`/robots`** — its own destination. The classic **Chat stays exactly as it is**; Robots is an additive second surface.
- **Role-branded agents** (Finance Agent, Marketing Agent, Sales Agent… one per department, with the department's accent + icon) instead of one-shot chats — **standing teammates** that work and check in with you when they need a decision.
- **Triage-first email console (per robot type).** Robots are now organised by **type** (a registry: **Email** is live; Scheduled report / Ads manager / Monitor are declared and plug in as their own console — the host routes by `robot.type`). Open an **email robot** and you get a **triage inbox**, not a settings page:
  - **Needs you, first.** Email robots default to **auto + escalate** (a quiet inbox), so the top of the screen shows only what needs a decision — **escalations first**, then any pending approvals — as cards; when there's nothing, an **"All clear · N handled today"** proof-of-work state. A "**checked Xm ago**" heartbeat + **"Check now"** (with a ping summary, "2 new · 1 replied · 1 for you").
  - **Tap-to-respond by intent.** Tapping an item opens a responder with the **full email**, the escalation reason, **quick chips** (Accept / Propose another time / Decline / Ask / Thank), and a one-line **"how should I respond?"** box — type *"say yes, propose Thursday 2pm"* and the robot **writes the full reply** for you to glance at and **Send** (recipient stays **locked** to the sender). Plus **Snooze / Archive / Forward** (forwarding only to an **admin-allowlisted** teammate).
  - **It learns (fewer escalations over time).** Tick **"handle emails like this automatically"** when you resolve one and it becomes a **standing rule** — grounded into the reply engine so the robot handles that kind of mail itself next time instead of escalating. Learned rules are visible + one-tap-removable in **⚙ Settings** (which also holds mandate / autonomy / triggers / mailbox / the forward allowlist).
  - An ambient **Timeline** (All / Replied / Flagged) shows everything it did. Escalated items now correctly reach **"Needs You"** + the sidebar badge (they were previously only in the activity feed).
- A guided **Hire wizard**: (1) pick the kind — **Customer assistant / Personal assistant / Department specialist** (this sets the robot's real reply persona, and Specialist reveals the department grid for its expertise) → (2) teach it (name, mandate, knowledge, escalation rules, signature) → (3) **connect its own mailbox** inline (Test connection; skippable — it stays paused until connected) → (4) autonomy + triggers → Activate. The roster and office show each robot's mailbox status ("connected ✓ / needs a mailbox").
- **Backed by a real, durable per-org engine** (`/api/orgs/:id/robots`): robots persist, run on the server, and their pending work fills the "Needs You" inbox. The **first working robot type is the email robot** (below) — connect a mailbox and a robot drafts real replies you approve & send. (Department-specific automations beyond email are the next build.)

## Core product & agent
- Autonomous agent loop — streaming, tool-calling, stall guard, context truncation, graceful error handling.
- **Shareable per-chat links** — every session has its own URL (`/s/<id>`) reflected in the address bar (deep-link / bookmark / reload reopens it — including older chats past the first page, fetched on demand; back-forward works), plus a **🔗 Link** button in the top bar to copy it. A link to a deleted or inaccessible chat shows a clear "this chat isn't available" panel (the URL is kept so it can be retried) rather than silently dumping you on the home screen.
- One seamless chat — no modes to pick. The user just talks; ArksAI reads the request and moves itself into whatever it needs — chat, plan, build (code), report, or image generation — with the right curated toolset. Under the hood there are still 4 modes (Chat / Plan / Code / Report) + capability tools, but the user never toggles them (a read-only chip in the TopBar shows what it's doing). Power users can still force one with `/mode`.
- Tooling: file read/write/edit, glob/grep, bash + persistent background processes, git, web search/fetch.

## Orchestration & engines
- **One engine: MiniMax.** ArksAI runs entirely on MiniMax — the LLM brain (M3 + the fast M2.7-highspeed model) and all multimodal capabilities (vision, image, speech, video). No model menu for everyday use: the chat picks the model itself.
- **ArksAI Auto (the default)** — picks the concrete model per task: **M3** for quality/visual/agentic/report/legal work, the **fast model (Flash)** for quick/light turns; escalates Flash → M3 when verification needs more muscle. Server-authoritative cost in the footer. Power users can still force **ArksAI Max** (M3) or **ArksAI Flash** (M2.7-highspeed) via `/model` or the advanced New-session dialog.
- **ArksAI Max** — MiniMax M3. Called via M3's **Anthropic-compatible endpoint** (thinking off by default → fast, decisive tool use; the OpenAI surface forces unbounded thinking and stalls), through an adapter that keeps the rest of the agent loop unchanged. **Never hangs, quality kept first:** the rare long-build "hang" was root-caused (raw-API probing) to **server-side starvation when several M3 turns run at once** — the losers get keepalive pings (so a gap-based timer never trips) while producing no output. Fixed with **(a) a global concurrency limiter** (caps simultaneous M3 streams so they can't starve each other; excess turns queue), **(b) a content-based stall detector** (the idle timer resets only on *real* content, not pings, so a starved no-output turn is caught and the run auto-switches **within MiniMax to the fast model** to finish), and **(c) a quality-first policy on big outputs** — large single-shot generations (a full spreadsheet/deck/doc) are now *allowed to finish on M3* rather than bailing early to a weaker model (a head-to-head bake-off showed M3 completes a detailed 3-statement financial model with hundreds of live cross-sheet formulas, where the alternative didn't finish). A turn that's genuinely large surfaces a **"still working — hang tight"** note so a long-but-healthy build never looks frozen. **Quality-first stall recovery is per-turn:** a single slow M3 step finishes on the fast model for *that step only* and the run then **returns to M3** (each staged build step is small, and M3 references cells far more accurately on a financial model) — only after repeated stalls does the whole run drop to the fast model.
- **MiniMax capability tools:** `see_image` (vision), `generate_image`, `text_to_speech`, `generate_video` (Hailuo).
- **Suno** music engine — full toolkit, per-track cost: `generate_music` (AUTO mode from a description, or CUSTOM mode with a rich ~1000-char style field + structured lyrics; controls for vocal gender, style weight, weirdness, and negative tags to exclude styles), `generate_lyrics` (structured words only, no audio — free), `extend_music` (lengthen/continue a prior track), and `cover_audio` (AI-cover a source track in a new style). The agent is steered as a Suno expert (style = comma-separated components, vocal cues in parens, strongest line first) and confirms the brief before the first paid generation. Default model is config-driven (`SUNO_MODEL`).

## One-shot quality system
- Task classification (`taskProfile`) → deliverable type + isVisual + tier.
- **Art-direction-first design — bespoke per subject, not a house template** (`design_direction`) — the biggest quality lever: before a brand/marketing/portfolio site is built, the agent **locks a bespoke design concept grounded in the subject's real world** (an immigration consultancy → "Port of Entry", travel documents — where the page *structure* encodes something true, e.g. real country/airport codes, never generic 01/02/03), commits to a **deliberate type trio** (display / body / a **mono DATA face** for codes·labels·figures — the cheapest tell of expensive editorial design), a **concept-grounded palette with a rationale**, and **one meaningful signature element**. It writes a durable, inspectable artifact (`design-direction.json` + `DESIGN.md` + a generated `tokens.css`) that the build reads and the design gate **enforces** — so the look holds across a long build instead of drifting back to defaults. The agent **names and avoids the AI-default looks** (generic minimal-muted blue-on-white, cream+serif+terracotta, black+acid-green, broadsheet hairlines) — "minimal · muted" is now **one deliberate option, not the mandated house style**. For a quick ask it runs silently with a sensible concept; for a brand it surfaces the one-line concept first.
- **Curated design menu (the quick-pick fallback)** — when a full art-direction pass isn't needed, the bundled UI kit still offers a restrained menu: **5 complete design kits** (`data-kit`: minimal/paper/linen/calm/harbor), **10 muted colour themes** (`data-theme`: slate, ink, indigo, ocean, sage, teal, clay, stone, plum, olive), and **10 typography pairings** (`data-type`: geometric · editorial · clean · startup · tech · journal · warm · humanist · **grotesk** · **institutional** — the last two adding deliberate faces + a mono role). All from **20+ self-hosted typefaces**, curated toward a **smooth, calm, uniform** set — calm/vintage serifs (Source Serif 4, Lora, Newsreader) + clean sans (Inter, DM Sans, Manrope, Plus Jakarta, Outfit) + a mono data role (**IBM Plex Mono**, **Space Mono**); the agent is steered AWAY from irregular/spiky display faces, because distinctiveness comes from the concept + palette + signature, never a loud font (no network needed) plus a new **`craft.css`** of high-craft primitives + meaningful **signature components built robust by construction** (`.eyebrow-rule`, `.board`, `.spec`, `.stamp`, and a clip-safe **`.ticket`** boarding-pass/receipt card — overflow-hidden, no rotation traps, stub that reflows instead of colliding on a phone) so an ambitious signature is *composed from a proven component* instead of hand-built and debugged for twenty rounds. It also ships a **reduced-motion-safe motion layer** — `.nav-underline`, `.lift`, `.tilt`, `.sheen` (CTA light-sweep), `.with-arrow`, `.float`, plus the scaffold's `site.js` wiring **`[data-reveal]` scroll-in + `[data-count]` stat count-up** for free, and a curated **hero-engagement** set (`.ken-burns` background drift, `.gradient-drift`, pointer `[data-tilt]`, and a LIGHT transform-only `[data-parallax]`) — the agent picks **one** that fits the brand (never forced, never heavy scroll-jacked parallax), all **desktop-pointer-gated and auto-off under reduced-motion**, transform/opacity only so there's no jank — so pages feel alive, not static. **Modern techniques, used with restraint**: a legible-by-default **glassmorphism** utility (`.glass` / `.glass-nav` — frosted with `backdrop-filter`, near-solid fallback so text stays AA, and a `prefers-reduced-transparency` solid path), a vendored **Open Props** subset (MIT, self-hosted — richer easings, 25 keyframe animations, 30 gradients), and **careful colour systems** (the locked palette now derives a proper accent **ramp** — `--accent-deep` / `--accent-2` / `--accent-tint` via `color-mix` — plus glass tokens, so the accent reads considered, not flat). Every technique is steered to stay **minimal · modern · polished · fully responsive** — a kit is a shortcut to the bar, never an excuse to drop below it. The menu is the muted fallback; `design_direction` is preferred for anything branded. Same system powers websites, reports and decks for one consistent identity.
- Opinionated design system + a bundled UI kit (tokens/components/themes, `add_ui_kit`) injected for visual tasks; per-type design standards (web/app, report, docx, xlsx, pptx). The design contract is **typography-first, minimal, and high-quality by default**: a real modular type scale + refined font pairing, a **distinctive confident palette** (not the generic "AI-default" blue) drawn from a **curated 28-palette swatch book** (`server/src/agent/palettes.ts` + the UI-kit `data-theme` set) — a deep **confident/vivid tier** (emerald, cobalt, grape, crimson, coral, amber, midnight… matched to the subject) alongside the quiet muted tier, **every accent pre-validated for WCAG-AA** against its button text and offered to the agent as a named menu so the colour layer is good *and* fast by construction (no more falling back to a generic grey-blue) — plus `validate_palette` for any custom pair, purposeful **micro-interactions** (hover/focus/enter, reduced-motion respected), real interactive/empty/loading/error states, and a senior-design-director self-critique. Enforced, not just suggested: the build gate runs a **deterministic mobile-responsive check** (renders at 390px and hard-fails a layout that overflows the screen), a **deterministic text-legibility check** (measures WCAG contrast on every text block vs its background — including copy placed directly in section bands, cards and heroes, not just `<p>` tags — and hard-fails washed-out muted text or borderline-low-contrast buttons that vanish into the page; a muted tone is allowed only while it stays legible) **including interaction states** (it actually hovers every button/link and re-checks contrast, so a control whose background changes on hover but whose text colour doesn't — making the label disappear — is caught, not just the resting state) **and BOTH colour schemes** (it re-runs the contrast measurement under emulated `prefers-color-scheme: dark`, so a half-baked dark theme — text token flips light but the page background stays light, invisible to a light-only check — is caught before it ships to the ~half of phones in dark mode; it also steers the agent to either pin `color-scheme: light` or implement dark mode fully, and to keep design tokens in one clean `:root` so `--accent`/`--ink` always resolve), plus the M3 design-director rubric — now upgraded to judge **distinctiveness FIRST** (competent-but-generic is a *fail*: it flags the named AI-default looks, rewards a deliberate concept carried through type+colour+structure and a meaningful signature element, and — when a `design_direction` is locked — checks the built page for **concept fidelity**), as well as any hard-to-read text over an image, so an output that isn't responsive, has illegible copy, or just looks like a template gets revised before it ships.
- **Design-brief compiler — turns a casual ask into an expert brief before the build** (`server/src/agent/designBrief.ts`): the per-request "think first" step (the planning a senior designer does in their head before touching the canvas). Auto-Brief deliberately skips visual work, so an artifact/app used to get the big *static* design system + the user's *raw casual* prompt and nothing in between — and a one-liner vs an expert spec produce wildly different output from the same model. Now, for a visual build, an **upfront bounded M3 pass rewrites the request into a tight, specific build brief** — concept (grounded in the subject) · a fitting palette **by name** · type roles (display/body/mono-data) · concrete layout · the ONE signature moment · real sample data · craft details · an **AVOID list** (emoji-as-icons, dead grey, generic centered-hero-glow, edge-bleed) — which the build then follows. Result: *"make me a little thing to track how much water I drink"* (no design hints at all) produced a floating card with a progress-ring signature, a fitting blue palette, mono tabular figures, an inline line-SVG drop icon and quick-add controls — Claude-quality from a one-liner, with **no hand-fed reference**. Fail-open (key off / error / timeout → the build proceeds unchanged); `DESIGN_BRIEF` config, on by default; emits an "understanding" beat so the upfront thinking is visible.
- **First-try correctness — compose proven blocks + self-check before finishing** (the answer to "latency"): the real cost of a slow build was never the model's thinking time, it was the **iteration to fix defects** — the agent would hand-build a fragile thing (an SVG progress ring, a 3-statement model, a stat grid), then loop through the verify/design gate to debug it. Two reinforcing fixes. **(1) Correct-by-construction blocks** the agent now composes instead of hand-rolling: a **`.gauge` progress ring** drawn by `stroke-dasharray` from a single `--val` (no rotation — the exact trap that used to burn 20+ inspect passes), a **`.stat` KPI card** (tabular figures + a currentColor up/down/flat trend arrow, no emoji), a **responsive `.table-wrap`/`.table`** (scrolls instead of overflowing a phone), and a **`financial-model` spreadsheet template** (`generate_spreadsheet template:"financial-model"`) that emits a complete Assumptions → Income → Cash-Flow model with **live cross-sheet formulas and a populated Cash Flow by construction** — so the empty-Cash-Flow / hard-coded-model defect can't happen. **(2) A cheap pre-completion self-audit** (`runCheapSelfAudit`) runs the deterministic, model-free defect checks (web hygiene — missing viewport / broken local asset refs; the xlsx formula/banner/section/numeric audits) **before** the expensive gate, so the agent fixes a known-bad result *in-context* with **no vision call and no full re-loop**; it's bounded by its own counter, independent of the verify/design budgets, and the gates still run afterwards as a backstop (now usually finding nothing). Paired with a front-loaded **Definition-of-Done** checklist injected into the system prompt (the exact bar the gate enforces, in the prompt up front) so the first build aims at it. Result: defects are prevented or fixed early, so the gates and inspect loops rarely fire — the build is right sooner.
- **Shared icon library — one beautiful Lucide set, everywhere** (`server/src/agent/tools/icons.ts`): a curated 120+ line-icon set (24×24, consistent 1.75 stroke) grouped by purpose — brand/lifestyle (coffee, leaf, gift, heart, sparkles…), nature/weather, communication (mail, send, phone, bell…), commerce (shopping-cart, tag, wallet…), data/charts, people, media, UI/navigation, places/travel and tech — used across **every surface**: websites & apps (shipped as a recolourable `icons.svg` sprite by `add_ui_kit`; reference with `<use href="ui-kit/icons.svg#coffee">` and tint via CSS `color`), reports & docs (inlined paths), decks (pptx KPI tiles), and social creatives. **One source of truth** (the sprite is generated from the icon library, with a drift guard test), and the available icon names are advertised to the agent in the tool results + design prompt — so it picks the *right* on-brand icon instead of hand-rolling mediocre SVGs or falling back to emoji.
- **Universal visual-quality gate** (`deliverableCheck`) — EVERY deliverable is rendered to image(s) and design-reviewed by a senior-design-director rubric (M3 vision), then bounded-revised: web apps (live Chromium), PDF reports/decks (mupdf raster, per page), .xlsx/.docx (HTML render), and .pptx (LibreOffice or a faithful preview). The same "looks perfect, works perfectly" guarantee across all types, not just web apps. **Reliable deck→PDF** (`convert_document`): converting a presentation to PDF renders the deck's faithful inline-SVG HTML mirror through headless Chromium, so charts and images come out crisp — sidestepping LibreOffice's habit of silently blanking embedded chart images on .pptx→pdf; plain office docs still fall back to LibreOffice, which handles text/tables well. A **deterministic, model-free structural pre-check** (per-page ink coverage **and per-page content extent**) catches both lonely near-empty pages **and under-filled pages** (content that stops high on the page leaving a big blank lower band — the ≥60% page-fill rule, which interior pages must meet; the cover and final page are exempt) instantly — even when no vision model is available — so each revise round is cheap and targeted (reports now allow up to 2 quality-first revise rounds). The gate also covers the cases that used to slip: generated **images** are validity-checked (a 0-byte / truncated / error-page download is rejected, not shipped); an **app built in report mode** gets a real runtime boot + smoke-test (not just doc rendering); the **formula audit** flags a typed-in derived row (Total/Growth/Margin) even when the rest of the model uses formulas; and if the visual review ever can't run (vision/renderer unavailable), it **says so out loud** instead of silently passing.
- **React + Tailwind path for complex apps (`create_react_app`)** — for a stateful, interactive web APP (a dashboard, a multi-view tool) where the React/Tailwind ecosystem earns its keep, the agent scaffolds a **Vite + React + TypeScript + Tailwind** app with **shadcn-style components** (Button/Card/Input/Label/Tabs/Dialog, all MIT, vendored into `src/components/ui`), pre-themed to the brand accent (hex → the shadcn HSL token), **self-hosted smooth fonts** (Inter + Source Serif 4, bundled by Vite with relative paths), and `base: './'` so it serves correctly at `/apps/<slug>/`. The existing **publish pipeline builds it** (runs the Vite build). Verified end to end (npm install + `tsc` + vite build + render). For a simple marketing/content site, the lighter vanilla `create_web_app` is still the default — the agent is steered to pick the right one. **Full-stack mode (`backend:true`)** also scaffolds a correct Express + SQLite server as ONE deployable service — the API routes (and an `/api` 404) are pre-wired BEFORE the SPA history fallback so `GET /api/*` always returns JSON (never the `Unexpected token '<'` trap), it reads `process.env.PORT`, and `npm start` serves the built SPA *and* the API on one port. Verified by booting it (CRUD persists to SQLite; unknown `/api/*` → JSON 404; client routes → index.html) and it's robust across Express 4 and 5. The canvas preview now RUNS that server for a full-stack app (so the API works in preview) instead of statically serving `dist/` on a colliding port.

- **Instant artifacts (`create_artifact`)** — turn a self-contained React component into a single, self-contained HTML file that renders **instantly with NO build** (the React runtime is vendored inline — no CDN, no npm install, no Vite). The JSX/TSX is compiled server-side (esbuild), the design tokens + a confident palette are baked in, and the component mounts to `#root`. The fast path for a small *visual* deliverable — a chart, calculator, interactive widget, a single landing section — it previews in the Canvas in ~1s and publishes as-is. Boot-verified: an interactive tip-calculator artifact rendered with zero console errors and live state updates. **Contrast is guaranteed** even though artifacts skip the build gate: a `theme:"dark"` option flips the whole token set to a coherent dark surface with **LIGHT ink**, and an always-on **runtime contrast guard** measures the background actually painted across the viewport and flips the ink tokens light/dark to match — so a component that paints a dark background while using the light text tokens can never render dark-on-dark (verified: a "focus timer" that previously showed near-invisible dark-on-navy text now measures 15.8:1 / AA, while a normal light artifact is left untouched). **Type is elegant + uniform by construction**: the artifact ships a cohesive font set **embedded as base64 woff2** — Inter (`--font-sans`, body/UI), **Space Grotesk** (`--font-display`, headings + large numerals — `h1–h4` use it automatically), **IBM Plex Mono** (`--font-mono`, tabular figures for timers/prices/stats), Source Serif 4 (`--font-serif`, editorial) — so the artifact renders in the *intended* faces on every device instead of falling back to a different system font each time (it previously referenced Inter/Source Serif but loaded neither). **Polish execution layer** (the difference between "clean template" and "expensive minimal"): a **bespoke TINTED neutral system** derived from the accent so bg/surface/ink/hairlines all share one undertone — warm accent → warm ivory, cool accent → cool slate — instead of dead grey (the single biggest polish tell); an **elevation scale** (`--shadow-sm/-md/-lg`) of soft, layered, accent-tinted shadows (lifted paper, not a hard drop shadow); an **optical type scale** (`--text-xs…-5xl` + `--tracking-*`) with per-size letter-spacing and tuned line-heights applied to headings by default; a radius scale; and refined **0-specificity defaults** (`:where(…)`) — a tasteful focus ring, smooth transitions, and a crafted look for an unstyled button/input — that any component style still overrides. In dark mode the neutrals tint to a deep accent-charcoal (not flat black) and the emphasis ramp brightens so accent-on-tint chips stay legible. Verified across warm/cool/dark palettes: the same restrained component renders polished and WCAG-AA in every case. (For a data-backed/multi-page app, `create_react_app` is still the path.)
- **Complete "looks" + a richer palette swatch book** — beyond the 10 quiet muted themes, a deep **confident/vivid tier** (emerald, cobalt, grape, crimson, coral, amber, midnight… 18 in all) and **9 complete "looks"** (`data-kit`: fresh, bold, studio, warm, tech, boutique, trust, vibrant, signal) that pair a vetted accent + a type pairing + a radius/shadow style in ONE pick — a high design floor instantly. **Every accent is WCAG-AA validated at generation**, the catalog (`palettes.ts` / `looks.ts`) is injected into the design prompt as a named menu, and the agent is steered to pick a *fitting, confident* colour by subject (verified live: a coffee-roastery build chose a warm burnt-orange `#b8541f`, not the old generic grey).
- **Real interactive components, self-hosted (`add_web_components`)** — when a site genuinely needs interactivity it would otherwise hand-roll (and then hand-debug), the agent installs a **lean, self-hosted Web Awesome / Shoelace runtime** (MIT, ~2.6MB — the TypeScript defs, React wrappers and the heavy Bootstrap-Icons bundle are stripped; component chrome uses an inline icon set) and drops in **`<sl-dialog>` (modal), `<sl-tab-group>`, `<sl-carousel>`, `<sl-tooltip>`, `<sl-dropdown>`/`<sl-menu>`, `<sl-details>` (accordion), `<sl-select>`, `<sl-switch>`** etc. in plain HTML — **no framework, no build step, no CDN**, lazy-loaded (only what you use is fetched). A **token bridge** maps the components onto the site's own `--accent` / `--font` / `--radius`, so they render minimal and on-brand (never Shoelace-default blue) and still pass the responsive + contrast gate. Verified to upgrade + theme correctly even when served from a subfolder like `/apps/<slug>/`. Gated behind the tool, so plain sites stay lean.
- **React + Tailwind apps (`create_react_app`)** — for a complex, stateful, interactive web app, scaffold a **Vite + React + TypeScript + Tailwind** project with **shadcn-style components** (Button/Card/Input/Label/Tabs/Dialog in `src/components/ui`), self-hosted Inter + Spectral fonts, and a minimal token theme pre-set to the brand accent (hex→HSL). It uses `base:"./"` so the built app works under `/apps/<slug>/`, and `publish_app` runs the Vite build. The **in-canvas preview "just works": for any build-to-static frontend (Vite/CRA/Astro/Vue/Angular/Parcel/Gatsby) the preview builds the app and serves the static output** (relative-pathed) rather than a dev server — so it renders reliably through the canvas proxy with no dev-server/HMR setup (SSR frameworks like Next keep running their own server; node apps preview on their own port). For a simple marketing/content site, `create_web_app` stays the lighter choice.
- **Websites — correct by construction (`create_web_app`)** — every website starts from a proven, responsive skeleton (the web counterpart of `create_expo_app` for Android), so the classic mobile failures are *structurally impossible*, not just caught later: an overflow-proof CSS reset (box-sizing, `max-width:100%` media, `overflow-x` guards), a **working hamburger nav** wired in `site.js`, a `<meta viewport>`, fluid type + auto-fit grids, and Home/About/Contact pages — plus the UI kit (incl. `craft.css`) copied in for richer components. The scaffold is now **theme-agnostic**: the structural guarantees live in `site.css` (mechanics), and the *look* lives in a separate `tokens.css` — so applying a bespoke `design_direction` never fights the reliable skeleton (the tool **preserves a locked `tokens.css`** instead of clobbering it). The agent fills in real content + theme + one meaningful signature, never the fragile layout/nav. The bundled scaffold is verified to pass the full mobile gate (no overflow at 320/390/768, the menu opens, zero hygiene defects) out of the box, so a generated site is right on a phone from the first render.
- Per-type functional check ("it actually works"): xlsx re-open + no #REF/error cells **+ calculation models must be formula-driven** (a finance/cash-flow/budget/forecast sheet built with hard-coded totals/balances/growth is auto-flagged and sent back to add live `=SUM(...)`/cross-sheet formulas — the vision gate can't catch this since it renders computed values, so this reads the cells' formulas directly); docx re-open + embedded fonts; pptx valid slides; pdf page/blank/bleed; apps boot + routes + interaction. **A numeric-sanity gate** then catches a model that's formula-driven but whose numbers still can't be right (the cross-reference failure mode): an **absurd outlier** (a 140‑million line in a small-business model — a formula that landed on the wrong cell), a **rate/percent leaked into a money column** (a revenue cell reading 0.30 instead of 6,000), or a **derived row (Total/Net/Balance) computing to 0** while real numbers exist — and a **section/divider-row detector** flags a plain-text or em-dash divider ("SPACE & LEASE", "—— REVENUE ——") interleaved in a calc sheet, since it shifts every row and corrupts absolute references. Both are deterministic (no vision needed) and feed the bounded revise loop.
- Vision runs on M3's Anthropic endpoint (thinking off → fast, decisive; bounded by a timeout so it degrades, never hangs).
- Visual model floor — non-trivial visual/report work never runs on the cheapest model.

## Bulletproof verification
- Static gate (typecheck/lint/test/build) + runtime gate (boots the app, exercises routes).
- **Code-review gate (works on a connected repo, not just "does it build")** — after the static checks pass, a second model reads the session's **actual git diff** (committed + uncommitted, vs the commit the workspace started from) and flags real defects the change *introduces*: correctness bugs (wrong condition/operator, missing `await`, null/undefined), regressions (a changed contract that breaks an existing caller), security issues on a new path, and leftover debug/throwaway code. Concrete findings are fed back into the same bounded-revise loop the design gate uses (capped, **fail-open** so a flaky review never blocks a verified ship). The agent is also told to **review its own `git diff`** (new `git_diff` tool — full unified diff) before finishing. On by default (`AGENT_CODE_REVIEW`), reviewer model configurable (`CODE_REVIEW_MODEL`, defaults to the run's model — the brain stays swappable).
- **Repository primer — the agent starts grounded on an existing codebase** — when a real repo is connected, the system prompt leads with a cheap, deterministic **`## Repository`** orientation: detected stack + frameworks, the package scripts, a shallow file tree, and the top of `AGENTS.md`/`CLAUDE.md`/`README`/`CONTRIBUTING` — so it answers questions and makes edits like a careful contributor instead of discovering the whole layout blind via glob/grep.
- Parameterized-route filling (`:id`/`{id}`/`<int:id>`/`:slug`) + an interaction pass (seeds inputs, submits a form, clicks primary buttons).
- Headless-Chromium UI smoke test (blank/console-error/failed-request detection) — now runs for **static sites too** (a plain HTML site is served + browser-checked during the build, not just at publish), so a static website can no longer skip the gate.
- **Multi-breakpoint check** — horizontal-overflow and the mobile-menu test run at **320 / 390 / 768px** (small phone, phone, tablet), so a layout that breaks at any common width is caught, not just one.
- **Mobile-menu check** — at phone width the gate finds the hamburger/menu toggle, taps it, and **fails the build if the navigation doesn't open** (no nav links appear). Catches the dead mobile menu that a desktop-width pass can't see, with an actionable fix note for the agent.
- **`inspect_ui` — the agent diagnoses complaints like a developer, not by guessing** — when you say anything in a built site "looks wrong / is broken / doesn't work / the X button does nothing", the agent opens the live app in a REAL browser (desktop + 390px mobile), **looks** at it (vision describes each view), **clicks every button/toggle and reports whether it actually did anything or is dead**, reads the **console/network** (uncaught JS errors, 404 assets/links/APIs), checks **mobile overflow**, and — when you name a thing — reports that element's **exact computed state** (hidden? what colour on what background? what size?). It's told to run this BEFORE editing (so it fixes the real cause, not a guess) and AGAIN after, to verify the fix actually worked — ending the blind edit-and-hope loops that burned tokens. Works for any complaint, not just mobile. **It also knows when to stop**: a per-build inspection budget + steering caps the inspect→fix→re-inspect loop so the agent doesn't whack-a-mole one hard element for hundreds of steps — once it's looked enough, it's told to ship or **simplify** a fragile element (use a robust `craft.css` component instead of fighting CSS), because a clean version that ships beats a pixel-perfect one that never does. A flaky/closed inspection now retries once so a round isn't wasted.
- **Libraries aren't booted like apps; static sites aren't mistaken for servers** — the runtime gate only tries to boot a project when its entry point **actually looks like a server** (uses Express·Fastify·Koa·Hono / `createServer` / binds `process.env.PORT`). A *library* or CLI runs its static checks + its own tests and skips the boot; and a **static client app is never misread as a server** just because its JavaScript contains common idioms like `app.run()` or `history.listen()` — so a plain site no longer dead-loops on a phantom "booting the app" failure.
- **Database-backed apps actually work, end to end (SQLite by default, Postgres provisioned)** — when an app needs to persist data server-side, publishing handles the database for it. **SQLite** is the zero-infra default (ships as a file with the app); **Postgres is fully supported** — publishing **provisions an isolated per-app Postgres database** (its own role + database on the managed instance), **injects the connection string** into the app at runtime (via its `.env`, loaded by the deployment even if the app doesn't use dotenv, and surviving restarts), and runs the app's `prisma migrate deploy` (→ `db push` fallback) + seed. Per-app credentials are derived deterministically so a re-publish reuses the same database and **data persists**. The agent is steered to pick one database + one migration and let the platform wire it (no hand-set URLs, no dual-schema tangles). A not-yet-supported DB (MySQL/Mongo/Redis) returns a clear, actionable message instead of deploying broken — and the provisioning layer is built to add those drivers next. (Postgres provisioning activates when the operator sets `MANAGED_PG_ADMIN_URL` to the managed instance; until then DB apps use SQLite.) **No leaks:** when a 24-hour preview expires or is deleted, its provisioned Postgres database **+ role are dropped** (the janitor reaps them, like the Android build droplet is always destroyed); a SQLite DB is just the file in the deployment dir, removed with it. Re-publishing the same app **reuses its database** (data persists); a superseded slug's database is reaped so nothing accumulates on the managed instance. The verify gate also won't dead-loop "booting the app" on a DB app it can't boot in the build sandbox. **Published apps serve cleanly behind the path proxy** (verified live with an Express + Postgres guestbook that persisted real form submissions): (a) the build step runs at `NODE_ENV=production` even though install ran at development for devDeps — Next.js inheriting development used to break its /404,/500 prerender; (b) the reverse-proxy forwards **any** request body content-type (a normal HTML `<form>` POSTs `application/x-www-form-urlencoded`, uploads send multipart) — Fastify previously 415'd those before the handler, so no-JS form submissions failed and the post-publish smoke test (which submits the first form) **false-marked working apps as errored**, withholding a live link for an app that worked; both fixed. The agent is steered toward a proxy-friendly stack (static/SPA + a simple Express/Fastify API, or a server-rendered Express app) and away from Next.js App Router/RSC for published data apps, whose RSC navigation fights the `/apps/<slug>/` rewrite. It's also steered to deliver **both deployment surfaces at once**: a **live preview URL now** (publish_app builds the app and serves it on ArksAI's own DigitalOcean infrastructure at `/apps/<slug>/`) **and** a **DigitalOcean App Platform–deployable repo** (a committed `app.yaml`) that auto-deploys when the user pushes to git. To be servable by publish_app the app is built as a **single web service at the workspace root** (one Express/Fastify server serving the built frontend *and* the API — one `npm install`/`build`/`start`), which is *also* a valid single-service DO App Platform app — so both are true together. Only when an app genuinely needs a **multi-service** architecture (separate static frontend + API + managed DB as distinct DO components) that the single-path preview can't serve as one unit does the agent **ask the user to choose**: a live ArksAI link now, or the multi-service DO App Platform auto-deploy. Installs are resilient too: `npm ci` falls back to `npm install` when a hand-authored lockfile is out of sync, instead of failing the publish. **Review happens BEFORE publication:** a freshly published app boots into a `verifying` state, is smoke-tested through the real public URL, and is only promoted to **live** once it passes (a failure is surfaced up front, never a broken link marked live).
- **Bounded inspection (no whack-a-mole, faster builds)** — `inspect_ui` is for diagnosing a *specific* reported defect, not proactive nit-hunting: a soft nudge kicks in after a few passes and a **hard ceiling refuses further inspections** in a build, so a run can't spiral into a 20-pass, 18-minute polish loop. The agent is also steered to treat its own "probably a false positive / rendering glitch / sub-pixel" findings as DONE — and to rely on the automatic verification gate rather than re-inspecting. Same output quality, a fraction of the time/cost.
- **Deterministic web-hygiene preflight** — source-level checks that even a headless browser can't see (most importantly a missing `<meta viewport>`, which Playwright hides because it sets the viewport itself): flags missing viewport, a hamburger with no wiring, fixed min-widths wider than a phone, **and a referenced local file that doesn't exist** — a `<link>`/`<script>`/`<img>` pointing at a workspace file that was never created (it 404s at runtime, so its CSS/JS/image is silently missing and the page renders broken — e.g. the recurring "linked `landing.css` but only created `site.css`" bug, where the bespoke signature element + lists fall back to unstyled defaults). The gate hard-fails with the exact missing filenames so the agent creates them or fixes the reference, instead of shipping a page with a broken signature — so the basics gate even with no Chromium/vision/egress.
- Post-publish smoke test of the real `/apps/<slug>/` URL — a broken deploy is caught and handed back to the agent, never the user.
- **Resilient app/preview proxy** — the reverse proxy that serves published apps (`/apps/<slug>/`) and the in-app preview reads the upstream response defensively and retries once on a dropped/stale connection, so a transient "premature close" can't surface as a 500 error page; an upstream that's genuinely down returns a clean "restart it" 502 instead.
- **Restart-resilient runs (no stuck spinner)** — a run interrupted by a server restart/deploy isn't lost OR left hanging: on boot the server clears any orphaned "running" session and **auto-resumes the recent ones** ("continue where you left off", recency- + crash-loop-guarded), and the **chat reconnects on its own** — a restart behind the proxy 502s and permanently closes the event stream, so the client now reconnects with backoff and **re-syncs the session on every reconnect**, reflecting the resumed run or cleanly ending it. The "working…" spinner can no longer hang forever after an update.
- **Resilient model streaming** — if the connection to the model drops mid-reply (a "premature close" / terminated socket), the agent reconnects and redoes the turn (bounded), and a `turn_reset` event clears any partial output so the retry never shows doubled text. If M3 stalls, the run switches within MiniMax to the fast model to finish — so a slow or flaky turn still completes instead of dying with an error.
- **Self-contained apps (no CDN)** — built apps vendor their libraries (charting, etc.) locally and self-host fonts, with one real root `index.html`; nothing is pulled from an external CDN at runtime, so a published dashboard's charts can't silently break when a third-party CDN rate-limits/403s.

## Deliverables & deployment
- **Publish & share a 24-hour preview** (`publish_app` + the TopBar "Publish & share") — ship a site/app to a **public URL anyone can open, no login** at `/apps/<slug>/`, served via a process registry that survives restarts (boot recovery). **Any app type works**: a plain static site, a **React/Vite (or CRA/Vue/Parcel) SPA** — which is *built* (`npm run build`) and served from its `dist/`, never run as a dev server — and **Node/Python server apps**, reverse-proxied. A small injected shim makes a published app's root-absolute calls (`fetch('/api/…')`, XHR, WebSocket) and assets resolve correctly under the `/apps/<slug>/` path, so an app's API actually works in the browser, not just the page load. Every publish is a **24-hour preview**: a boot-started janitor auto-deletes it (process + files + record) 24h after publishing; re-publish to refresh. The dialog shows a live "expires in …" countdown. Opening a published link from the **installed PWA** hands off to the user's real browser (a true external window) instead of taking over the app window, so the ArksAI session is preserved. (Single-Droplet constraint for now — a permanent tier comes with a bigger server; pre-existing deployments without an expiry are left running.)
- Auto-export (zip download chip) + auto-canvas — the canvas auto-opens and loads the result (web app, PDF, spreadsheet, or doc). Generated **compliance machine files** (WPS `.sif`, PINT AE e-invoice `.xml`) are surfaced as downloads too, so a produced filing actually reaches the user. **The downloads list is the finished thing, not the workshop floor:** build **intermediates** that only exist to be embedded into a deliverable — rasterised icons (`icon-4-0.png`), slide-chart images, `render_chart` SVGs under `charts/`, and the `.pptx`/artifact `.preview.html` mirror — are filtered out, and **revise-round versions are collapsed to the latest** (one `deck.pdf`, not `deck.pdf` + `deck-v2.pdf` + `deck-v3.pdf`), so a single deck no longer buries you under a dozen files. The dedup is conservative — it only merges an explicit `-v2`/`(2)`/`-final` suffix on an otherwise-identical name, so distinct files like `sales-2024.pdf` and `sales-2025.pdf` are never merged.
- Styled office docs: `generate_spreadsheet` (exceljs, formula-driven, validated — and a built-in **formula recalculator** recomputes each formula's cached value before saving, so the in-app preview shows correct numbers instead of a model's stale/0/blank cached value; this now runs **authoritatively on the built workbook using each cell's real coordinates**, so it can't be defeated by a title row, merged cells or object-keyed rows that previously left formula cells blank in the preview; the formula is preserved so the download always recalculates in Excel — and **every formula cell is guaranteed to survive**: ExcelJS silently drops a formula that has no cached result, so a formula our evaluator can't compute (NPV/IRR/lookup, refs to text) used to vanish entirely — it now always keeps a placeholder result so even advanced formulas are preserved, never lost). **Large, granular, multi-sheet models build incrementally** — a 3-year **month-by-month CAPEX + OPEX** model (Assumptions → CAPEX → OPEX → Personnel → Summary, with cross-sheet formulas) is assembled **one sheet per call** (`append: true`) instead of one huge payload, so a detailed model **reliably finishes and returns output** rather than stalling, while staying fully formula-driven and gate-passing. **Total/roll-up rows are auto-styled** (bold + a hairline top rule) so a model reads like a real financial statement. **Cross-sheet links can't silently break**: a model that writes a reference without the leading `=` (e.g. `Assumptions!$B$10` typed as plain text — which used to sit inert and break every dependent cell with `#VALUE!`) is **auto-healed into a live formula**, the design gate **flags any stringy reference that slips through**, and every workbook is marked **recalculate-on-open** so Excel/Sheets always show correct numbers. The preview recalculator now also evaluates **`IF()` and comparison conditions** (`>`, `<`, `>=`, `<=`, `=`, `<>`), so an `IF(C4>0,…)`-driven row and everything downstream show the right values, not 0. The model is steered to a **clean calc structure** (header = row 1, data = row 2+, no decorative banner/title rows inside a calc sheet) with a deterministic **banner-row detector** that flags a `── SECTION ──`-style row which would shift cells and corrupt formula references, so totals/balances point at the right numbers, and to **research real drivers** (rents, salaries, equipment costs) for the Assumptions sheet rather than inventing figures. **Authoritative recalc + a blessed "build it by hand when needed" path (`recalc_spreadsheet`)** — the in-tool calculator covers SUM/IF/arithmetic/cross-sheet refs, but a real model often needs functions it can't compute (NPV/IRR/VLOOKUP/INDEX-MATCH/dates) or circular links (interest↔debt↔cash). For those, the agent is now explicitly cleared to do what an expert does — **build the model with a Python/openpyxl script** (real formulas, never dumped literals) — and then call **`recalc_spreadsheet`**, which runs the workbook through headless **LibreOffice** to compute EVERY value authoritatively, writes the true results back so the preview and first open are correct, and reports any **error cells** (#REF!/#VALUE!/#DIV0!) in ONE trustworthy check (no more hand-looping LibreOffice to verify). The **delivery gate runs the same LibreOffice recalc on every model**, so even a workbook the agent didn't explicitly verify ships with correct numbers and a real error-cell check (degrades to the built-in calculator when LibreOffice is unavailable). The guiding rule: a correct model is worth a longer build — a wrong-but-fast model is the failure. (The full set of spreadsheet failure modes + their handlers is catalogued in `SPREADSHEET_EDGE_CASES.md`.) `generate_doc` (docx) — documents embed the editorial typefaces (Source Serif 4 display + Inter body, the same as the reports/app), so they render designed everywhere instead of as office default. `generate_doc` also takes a **designed cover page** (masthead · accent title · one-line thesis · a **KPI band** of headline numbers · metadata footer) and `chart` blocks that embed **publication-grade `render_chart` images** — so a brief/report reads designed end-to-end, not as a wall of text.
- **`generate_pptx`** — real, editable PowerPoint (PptxGenJS): editorial 16:9 decks with a **designed cover** (masthead · accent title + thesis · a **KPI band** of headline numbers · metadata footer · `CONFIDENTIAL`) and a **dark/light slide rhythm** (per-slide theme), **publication-grade charts** via `render_chart` (dual-axis/heatmap/… embedded as crisp images, beyond the basic native bar/line/pie), title/section/bullets/two-col/stat/quote/table/image layouts, one accent, and an embedded preview for the canvas + the visual gate.
- Report mode — PDFs and 16:9 decks with a full editorial protocol (newspaper margins, anti-orphan `.lede`, kickers, rules, page mechanics); charts/figures are ATOMIC (`.keep`/`.fig`) so nothing splits across a page, and every page is auto design-reviewed before delivery. A **"get the first render right"** rule set targets the three defects the gate used to churn on — **lonely / half-empty pages** (forced per-section page-breaks are now forbidden; content FLOWS to fill ~85–100% of every page, a stray card grid sits with its narrative, never alone), **cornered/tiny charts** (every chart is a full-measure `.fig` on its own row and the SVG is auto-made **fluid** so it fills the column instead of collapsing with colliding axis labels), and the **white-frame background** (the page colour lives only on html/body or a `.bleed` page) — so the first render passes review fast instead of looping expensive revise rounds. **Token-efficient by design:** once the PDF/deck is rendered, the raw web-research dumps from earlier turns (web_search / web_fetch / fetch_data — already baked into the document) are auto-trimmed from context so the QC/revise turns don't re-pay for them, cutting a research report's token use dramatically. If a run ever does brush the per-run safety budget **after a good document was produced**, it now **completes normally and shows the file** (with a soft "this took a bit more processing" note) instead of erroring over a finished PDF. The protocol also hardens the anti-half-empty rule (NO interior page below ~70% full — a short profile/overview section merges with its neighbour) and enforces a single **output language** (English, or the user's language) so stray non-Latin characters never leak into the prose.
- **`render_chart`** — publication-grade charts as embeddable SVG (Vega-Lite → SVG, server-side, no browser/Python): line, multi-line, **dual-axis** (volume bars + a trend line), bar/bar-h, stacked, area, donut, and **heatmap** (e.g. month×year). Editorial defaults baked in — flat 2D, muted base + the report accent on the key series only, direct value labels, light gridlines — so charts are on-brand by default and inline straight into the report HTML. The returned SVG is **fluid** (full-measure `width:100%; height:auto`, viewBox kept) so it fills its `.fig` block instead of collapsing into a corner, and the intrinsic size auto-grows with the data (more rows → taller) so axis labels never collide; it also rasterizes to a transparent PNG so the SAME editorial charts embed into `.pptx` decks and `.docx` documents. **A chart can never silently ship empty**: Vega will render valid-but-blank axes (no bars/line) when the `x`/`y`/`series`/`value` field names don't match the keys in the data rows — so `render_chart` now **validates the field binding up front** (and a post-render backstop checks a bar/area chart actually contains mark elements) and returns an actionable error listing the real data keys, instead of writing a dataless SVG that would inline into the report as empty axes. Caught live: a "Top 10 nations" horizontal bar chart that rendered as bare axes.
- **Two deterministic quality tools** — `validate_palette` checks a brand palette for **WCAG 2.2 AA contrast** (body text + links at 4.5:1, accent/large text/UI at 3:1) before any visual build and returns a corrected colour for any failing pair plus a ready-to-use token set (primary/accent/bg/surface/text/muted/line/link) so text is never shipped unreadable; `compute_financials` runs the **DCF (NPV + terminal value), the standard ratio set, budget variance (favourable/unfavourable), and a linear/growth forecast** so every derived number in a report or sheet is computed, not hand-typed. Both are pure, instant, no key needed, available in chat/code/report, and the relevant finance + design standards steer the agent to use them.
- **Designed, full-bleed cover** — the report cover is a **true edge-to-edge canvas** (a named zero-margin `@page` so the background field reaches all four paper edges — interior pages keep their margins), with a typography-led foreground: the **brand logo** in the masthead, accent title line, one-line thesis, a **KPI band** (even cell padding, breathing room), and a metadata footer. Dark / deep-accent / light field options.
- **Analysis & methodology rigor** — the report protocol now demands a systematic analysis pass first (profile columns, full cross-tabs, reconcile conflicting fields), an insight-led narrative (counter-intuitive reframe → evidence → ranked recs tied to specific data points), and a Methodology/Notes section (proxies + their limits, data gaps, source attribution).
- **Android Apps — a dedicated page** (`/android`, 📱 in the sidebar): a guided intake wizard (app name + what it does · app type/archetype · a **visual style kit** — Material You / Minimal-Editorial / Bold-Playful / Clean-Pro / Dark-Premium · how it runs: native APK / PWA / both · a broad set of **device capabilities** — camera/QR, photos, location, notifications, contacts, microphone, biometrics, calendar, files, audio/video, haptics, share, Bluetooth, NFC · accounts/sync/realtime backend · a 12-colour accent palette) composes a precise brief. Because a good native app needs a plan, the agent does a short **plan + clarifying round** (proposes screens, data model, flows, permissions; asks a couple of essential questions) and waits for approval before the long build — then builds fully autonomously and hands off to the live session view. Native APKs are compiled on an ephemeral build machine (Kotlin-pinned Expo prebuild + Gradle, never EAS) and returned as an installable file; if a backend is needed it auto-deploys to our infra and the client is wired with a typed JWT API. Honest about timing.
- **Publish to Google Play — per-org developer accounts**: each company connects its **own** Google Play Developer account on the Android page (admin-only), so apps publish under that company's identity + billing — never a shared account. The service-account credentials are stored AES-256-GCM encrypted at rest, write-only, org-isolated (admin-gated). *(Connection scaffold is live; direct-to-Play AAB upload is the next step — until then native builds hand back a sideloadable APK.)*
- In-app doc viewer (xlsx/csv/docx/pptx → styled HTML); **Canvas as a clean result viewer** — it no longer auto-pops a developer panel over the chat on completion; instead the clickable completion card is the moment, and tapping it opens a decluttered viewer (just a title · **Open ↗** · Close, with the finished result full-bleed). The port pills, file tree and refresh now live behind a single unobtrusive **Dev** toggle for power users — so a non-technical user never sees `:4000`/`:2024` port chrome, while everything stays one click away.
- **Mobile apps (in progress)** — a bundled **mobile UI kit** (React Native / Expo: light+dark design tokens, ThemeProvider/Screen/AppText/Button/Card/Field/EmptyState/Loading + a root crash-safe ErrorBoundary, `add_mobile_ui_kit`) and a matching **app backend kit** (Fastify + SQLite: JWT auth, a sample CRUD resource, a consistent error envelope, per-route JSON-schema validation, CORS, idempotent migrations, `add_app_backend`) that installs the API into `server/` **and a matching typed client into `src/api/`** (a JWT+AsyncStorage fetch wrapper that unwraps the error envelope, plus login/register/me and a single `API_BASE_URL`) — so a generated app's screens *and* its API are wired together out of the box: the backend deploys zero-config to our infra (`<slug>.apps.arksai.studio`), you set one URL, and every screen calls it the same safe way. Screens *and* the API both start from a minimal, modern, typography-first, validated foundation — the same house quality as the web builds. PWA is the default lightweight path; native Android APKs build on our own infra (Apple/iOS via EAS).

## Smart agent
- Sees **every** upload, automatically — on each run the agent is told exactly what was just uploaded and how to open it (images → `see_image`, **available in every mode**; a logo → `extract_palette` for exact brand hex; **spreadsheets (`.xlsx/.xls/.csv`) → `read_spreadsheet`**, which lists EVERY sheet with dimensions + headers + samples and reads exact values on request — never a lossy text dump that silently drops sheets, and heavy analysis crunches the raw file with Python; **presentations (`.pptx`) → `read_presentation`**, which reads every slide's title/bullets/tables + speaker notes (never a binary blob); prose docs (`.pdf/.docx`) → their auto-extracted `.extracted.txt` sidecar; anything else → `read_file`), so it acts without the user re-instructing. **When several files are dropped at once (multiple spreadsheets + images + a deck), it processes EVERY one** — every sheet, every slide, every image — not just the first. It never claims it "can't view" an image — vision is always on. Files attach via the `+` button, **drag-and-drop, or clipboard paste** (copy a file/screenshot → ⌘/Ctrl-V); a `📎` chip shows what's attached. Uploads **retry automatically** through a transient network or deploy/restart blip (with backoff; a real over-limit `413` still reports immediately), so a momentary hiccup never surfaces as a "failed to fetch".
- **Make an image LIKE an uploaded one** — `generate_image` takes an optional `reference_image`: to recreate or vary an image the user uploaded, the agent looks at it (`see_image`) to read its subject/style/composition/palette and prompts from that, and for a person whose likeness should carry across it passes the reference directly to the engine (MiniMax subject reference). "Create an image like this" just works.
- **Brand from the logo** — `extract_palette` reads the real colours out of an uploaded logo (deterministic, no vision model needed) so the accent is taken from the brand; the **same identity (logo, accent, type) is applied across every deliverable** — web apps, decks, docs, and reports — and a deliberately beautiful palette is chosen when there's no logo.
- Auto mode/engine switching — `switch_mode` lets a chat become a build/report mid-conversation; the runner reloads the toolset, prompt, and engine on the fly with an inline note. It also routes **back**: a build/report session isn't sticky — if your next message is a different kind of request (a question, a deck, an image, a brand-new build) ArksAI moves itself to the right mode for it instead of forcing it through the current one. Built into the seamless flow: a vague ask → ArksAI asks a short round of clarifying questions first (never refuses, never blindly guesses); a coding ask → it **plans first** (shows exactly what it'll build) and waits for the user to approve (→ autonomous build) or revise.
- Plan approval gate — when ArksAI plans a build it presents the plan, then shows an explicit **"✓ Approve & build" / "Revise"** card (Approve kicks off the autonomous build). **Revise** is now unambiguous: clicking it hides the approval card and drops you into a clearly-labelled **"Revising the plan"** compose mode — a banner above the message box (with a "Keep plan" escape that restores the card) and a revision-specific placeholder — so it's obvious your next message edits the plan, after which ArksAI re-plans and re-presents the gate. The gate is **structural**, not just a suggestion: building can only begin on your next turn after a plan — the agent cannot skip straight from planning to building in the same breath. Approve **reliably** starts the build: the plan must be complete (no trailing question) before it's offered, and on approval the agent is blocked from re-submitting the plan and goes straight to building (so Approve never loops back to the card).

## Day-to-day capabilities
- Recurring/scheduled tasks — a durable server scheduler (daily/weekly/interval) that fires a fresh session even with the browser closed; managed via a Schedules dialog. Times are read in **your local timezone** (captured from your browser, DST-correct), so "daily 08:00" fires at 08:00 where you are — not on the server's clock.
- **Large multi-tab spreadsheet reads — query, don't dump** (`query_spreadsheet`): the right way to analyse a big or many-tab workbook the way a senior analyst (or Claude) would — **load every tab into a DuckDB runtime and run SQL across them, getting back ONLY the result** (totals, group-bys, **joins across tabs**, pivots, filters, reconciliation) instead of paging thousands of raw cells into the chat. The data stays in a separate process, so it scales to huge, many-tab files without ever filling context. `read_spreadsheet` is now the cheap **map** (it lists every sheet with dims, a **query-table name**, **inferred column types**, and samples); `query_spreadsheet` is the calculator (each sheet is a `lower_snake_case` table; call once with empty SQL to discover the tables, then query). It also has a **`profile` mode** — the ideal first move on a messy/unfamiliar file: per-column **type, min/max, distinct count, average, and % null** for every tab, no cells paged. pandas + openpyxl + **duckdb are preinstalled** in the agent image so reads are instant (no mid-task `pip install`), with a graceful "install + retry" path if ever absent.
- Data in — `fetch_data` pulls a public CSV/JSON/published-Sheet URL (SSRF-guarded).
- **Ad-platform connectors (Meta · Google Ads · TikTok)** — org admins connect their ad accounts under **Settings → Connections** (OAuth); the agent then pulls **live** performance via `fetch_ads` straight into dashboards and reports (spend/impressions/clicks/ctr/conversions, by campaign/ad/day). Per-org, OAuth tokens stored **encrypted** (AES-256-GCM) and never exposed to the model; auto-refreshed on expiry; each provider gates on its app credentials. Reusable adapter framework (one interface per platform). Operator setup in `CONNECTORS.md`.
- **Connect your GitHub & push to your own repo (per-user OAuth)** — each user links their **own** GitHub account (OAuth App) and **picks which repository** ArksAI pushes generated code to, or **creates a new repo** right from the New-session dialog (searchable list of repos you can push to). The session's clone/push then use **your** token (falling back to the operator PAT only for self-host). Tokens are **encrypted at rest** (AES-256-GCM), never returned by any API or shown to the model, and **scrubbed from all git output**; strict **per-user isolation** (you can only ever use your own connection). The operator turns it on either via env (`GITHUB_OAUTH_CLIENT_ID/SECRET`) or, with no SSH, an operator endpoint that stores the app credentials encrypted at rest (flips it on instantly). A documented trade-off of the OAuth-App approach is the `repo` scope grants access to all your repos (a future GitHub-App upgrade would scope to chosen repos).

Now connecting a repo to an empty workspace **clones it in on demand** — eagerly on attach (with clone progress) and, as a guarantee, at the start of the next run — so the agent has the real code to read, answer about, and edit. An existing build in the workspace is never clobbered (that stays a pure push-target).

So "improve my code" lands as a reviewable PR + CI, not a surprise commit.

The **GitHub card** lets you connect/disconnect your account and **create a new repo right there**; the ad-platform connectors (Meta/Google/TikTok) live there too for admins. - **Prepaid org wallet + invoicing (USD-canonical)** — each organization has a **prepaid balance** it spends as it builds. - **Reads SCANNED PDFs by sight (accurate PDF→Excel)** — a text-only extractor (`pdf-parse`) returns *garbage* for scanned/image documents (e.g. bank challans, invoices), silently destroying a table's structure so the model has to guess — which drops suppliers, mis-files months, and scrambles totals. Now, when an uploaded PDF's text extract looks unreliable, ArksAI **renders each page to a high-resolution image** and routes the agent to **read the pages with vision (`see_image`)** instead of the dead text — the same way a person would. The steering also mandates the right discipline for document→spreadsheet work: **transcribe every line item** (with its own date/month, never inferred) into an **audit-trail sheet**, build the summary with **live formulas**, **reconcile each source document's extracted total to its printed total**, and **de-duplicate** repeated documents — so a missing row or a wrong month is *caught*, not shipped.
- Deliver out — `send_webhook` posts a result to a Slack/Zapier/Discord hook.
- **Email (per-org mailbox)** — each organization connects its own mailbox (SMTP for outbound, IMAP for inbound) in Settings → Email; passwords are stored **AES-256-GCM encrypted at rest** and never returned to the client. The agent can then `send_email` (with workspace attachments — a PDF, deck, sheet, or image) and `read_inbox` (triage/summarize/draft a reply), scoped strictly to the session's own org. A "Test connection" check verifies both legs before use.
- **One-step mailbox connect (auto-detect)** — connecting a mailbox (org OR per-robot) defaults to a **quick mode**: enter just the **email address + password** and ArksAI auto-discovers the SMTP/IMAP host, port and security, verifies the login, and saves — no server settings to look up. Detection escalates through a built-in provider table (Gmail/Outlook/Yahoo/iCloud/Zoho/GoDaddy/…), an **MX-record lookup** (Google Workspace / Microsoft 365 custom domains), then the **Mozilla/Thunderbird ISPDB** (`server/src/email/autoconfig.ts`, `POST …/email/autoconfig`). If detection or the sign-in fails, it **falls back to the manual form, pre-filled** with whatever was found (and a clear hint that 2FA accounts need an app password).

### The email robot (the engine behind the console)
- **Each robot has its own mailbox** (a Mailbox panel in the robot's office — SMTP + IMAP, encrypted at rest). Connect it and that robot becomes a working **email agent** with its own email identity: it polls *its* inbox and drafts a reply per new message, grounded in its mandate/knowledge. (An org-level mailbox also exists for the general chat/code agent's `send_email`/`read_inbox`.)
- **Drafts for approval (default)** — each reply waits in the **"Needs You" inbox** for one-tap **Approve & send** or Dismiss. Once trusted, set a robot to **auto-send**.
- **Safe by construction** — replies are **locked to the inbound sender** (a prompt-injected "forward to…" can't redirect them), the model sees only that one message plus the robot's own knowledge (data-minimized), and anything out of scope (refunds, billing, money, legal, angry complaints) **escalates to a human**.
- **Model choice** — robots draft with **ArksAI Max (M3)** or **ArksAI v4 (DeepSeek)**, or **Compare both**.

## Organizations (multi-tenant "spaces")
- **Isolated org spaces** — every session/project/deployment is scoped to an org; **everyone — members AND the platform operator — sees only their own workspace's data** (cross-org access → 404). The operator's **super-admin** role unlocks platform administration (provisioning orgs, reviewing the waitlist, managing any org's members), **not** a commingled view of other orgs' chats.
- **Roles**: super-admin (operator) → org **admin** → **member**; new sessions/projects are stamped with the creator's org.
- **Project-level visibility** — each project is org-wide by default, or **private to its creator + invited members** (enforced in every list/get query; cross-visibility access → 404). The owner or an admin manages sharing.
- **Invite-only, link-based onboarding** (no email infra): the super-admin creates an org + invites its admin; org admins invite their team — each invite is a one-time link to copy/share. Opening it sets a password and logs the member straight in; memberships revoke instantly (killing live sessions). Being **granted access removes that person from the waitlist** automatically (on invite issue and on accept), so the operator's review list only shows people not yet actioned.
- **In-app admin panel**: create orgs, **delete an org and ALL its data** (operator-only, cascades sessions/projects/published apps/schedules/commands/profile/analytics + removes member accounts orphaned by the deletion; the Default workspace is protected), review the waitlist (leads), manage members + invite links; team-member email login (the platform operator signs in separately at the unlinked `/operator`) and an `/invite/<token>` accept page. The invite field is a prominent full-width email; **free/personal email domains are blocked** (server-authoritative, gmail/outlook/…) and an invite whose domain differs from the admin's own is **flagged as out-of-org** (confirm to proceed). A company's workspace is its OWN and is **not swappable** — there is no workspace switcher in the UI for anyone (the sidebar just names the current workspace).
- **Cross-org isolation, audited & hardened** — every user-facing resource is scoped to the authenticated org (never a client-supplied id): sessions + all `/api/sessions/:id/*`, projects (+ creator/invited visibility), **the live sidebar event stream** (a tenant only receives its own org's session status/titles), **deployments** (list + stop/restart/delete — a slug from another org → 404), **schedules** (list/create/enable/delete, and a fired run lands in the owning org), **custom commands** (per-org keyed `(org_id, name)` so orgs never see/overwrite each other's), and org **memory**. Mutating a project (edit/delete/upload) additionally requires being its owner or an org admin. Backed by isolation tests **including an HTTP-level red-team** that signs in as one org and confirms it cannot reach another org's data on any route (list, by-id, sub-routes, or destructive writes) — and a check that the **operator** is confined to its own workspace (it opens its own chats but gets a 404 on another org's session/events/projects/schedules/deployments) while keeping the admin provisioning surface.
- Shipped **non-breaking**: the existing operator login keeps its platform-admin powers via the super-admin role (now scoped to its own workspace for data reads, like every tenant), and all prior data lives in a bootstrapped "Default" org.
- **Per-org shared brain + an onboarding designed to be FINISHED** — a new org admin gets a fully-visible, agent-led first run built on how anticipation works (dopamine = a seeking signal driven by a reward that beats expectation): a vivid promise + one tiny ask opens a loop they want to close, an **endowed 3-step tracker** (Brand → Profile → First build) shows them already moving, and a **live brand-reveal panel** beside the chat lights up with their real accent, palette and "about" the moment ArksAI reads their site or logo — the studio visibly becomes theirs. ArksAI **crawls the org's website** **or reads an uploaded logo's colours** (`extract_palette`, deterministic — and vision works in every mode, so it never claims it can't see the image), saves the brand early so the panel pops, asks a couple of quick questions, then `save_org_profile` (complete) and tees up an exciting first build. That brand + "about" + a recalled digest of the org's own past chats are injected into **every** session in the org (brand applied consistently unless the user overrides). Members joining later inherit it silently; the admin can re-run/skip/edit.
- **Strict per-org memory isolation** — org memory lives under an `org:<id>` scope derived only from the authenticated identity (never client input). A tenant org reads/writes **only its own** scope — never the deployment-`global` notes, never another org — enforced in the runner's context builder *and* the memory API (read/write/delete), with repo memory namespaced per org. Cross-org isolation is unit-tested.

## Analytics & insight (admin)
- **User feedback / rating system** — every finished result carries a quick **👍 / 👎**, and a thumbs-down opens a short "what's wrong?" box for the user's own words. Ratings are captured server-side (`feedback` table), **org-scoped** (a complaint is never attributed to or readable by another org), and **content-safe** (a write-side allowlist persists only metadata — mode/task/deliverable kind/name — so raw chat or document text can never leak into a feedback record). The **operator console** shows "What users said" — the down-rated complaints with their context, a 👍/👎 tally and an open-complaints count, each markable reviewed — so the team sees exactly what's failing and can act on it. (Endpoints: `POST /api/sessions/:id/feedback`; super-admin `GET/PATCH /api/admin/feedback`.)
- **Country-specific cost display (per-org currency)** — costs are computed in USD but **shown in each organization's chosen currency**, starting with **AED** (the platform default). An admin picks the org's currency in the Admin panel and it flows everywhere cost appears — the per-session cost bar, the `/cost` command, and the operator + per-org analytics consoles (KPIs, charts, tables). GCC currencies are USD-pegged at fixed rates (AED 3.6725, plus SAR/QAR/BHD/OMR), so conversions are exact with no rate feed; more currencies can be added later.
- **Operator analytics console** (super-admin, full-screen from the sidebar) — a **dense, editorial "data desk"** (tabular figures, hairline rules, **week-over-week delta chips + inline sparklines** on every headline metric for fast reading) to understand how the whole platform is used at a glance: headline KPIs (active users 7d/30d, **stickiness = DAU/MAU**, sessions, success rate, **time-to-first-build**, cost, orgs/users, live apps, waitlist), active-users/sessions/cost-per-day trends, the **acquisition funnel** (lead → signup → onboarded → built → published), **feature adoption** by play, splits by mode and model, quality (done vs error), cost by model, a **signup-cohort retention** grid, and named **per-org and per-user drill-down** tables.
- **Per-user drill-down** — click any user (operator) or member (org admin) to open a metadata-only detail panel: their sessions, success rate, cost, time-to-first-build, a 30-day activity chart, what they build (plays/modes/models), and their orgs — scoped to the viewer's permissions.
- **Activation: time-to-first-build** — median time from signup to a user's first build, surfaced as a KPI and per-user, so onboarding friction is visible.
- **Actionable alerts (no setup)** — derived from existing metrics with no thresholds to configure: **cost-spike** detection (an org's last-7-days spend vs its trailing weekly baseline) and **churn-risk** orgs (onboarded + once-active but gone quiet) for the operator; per-org admins see their own cost-spike + inactive members. Quiet by default — shows "all clear" when nothing's wrong.
- **Scheduled digests** — a periodic platform snapshot (every `ANALYTICS_DIGEST_HOURS`, default daily) is computed and stored for the operator to review in-app (with deltas vs the previous one), and pushed to a webhook if `ANALYTICS_DIGEST_WEBHOOK` (Slack/Zapier/…) is configured.
- **CSV export** — one-click download of the orgs, users, and per-org members tables (client-side, no round-trip).
- **Per-org dashboards** — an org admin (or the operator drilling in) gets the focused subset inside the admin panel's **Usage & engagement** tab: engagement KPIs, active-members/sessions trends, the activation funnel, what the team builds (plays/modes/models), retention cohorts, alerts, and a clickable per-member activity table — scoped strictly to that org.
- **Lightweight event-tracking layer** — a non-blocking `track()` writes usage events (`app_open`, `run_finished`, …) to an `analytics_events` table with a precomputed epoch-day bucket (zero date-SQL, SQLite+Postgres portable); metrics also derive from existing tables so they work from day one and get richer as events accrue.
- **Privacy is absolute — metadata only.** Analytics read only counts, timestamps, status, mode/model, the play key, tokens and cost; they **never** touch the `timeline` table or any message/document content. Enforced at both boundaries (a write-side scalar-only `props` allowlist + a grep-able test that the analytics modules contain no content reads) and gated end-to-end: operator routes are super-admin-only, per-org routes require that org's admin (a per-user drill is membership-gated so an admin can't probe non-members) — covered by an HTTP red-team test (a non-operator gets 403 on platform analytics; an org admin cannot read another org's).
