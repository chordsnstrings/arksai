# SCAFFOLD_PLAN — predictable outputs for ANY app, on ANY stack (2026-07-02)

## The thesis (proven, not aspirational)
Every serious defect this week was **template-preventable**: TaskForge's `mergeParams` bug,
snake_case/camelCase contract drift, seed-credential mismatch, CSS cascade order, the
publish single-service shape. And the bake-offs proved the converse: with a template-owned
skeleton, a $0.001 model's deck was indistinguishable from the premium tier. So:

> **The skeleton owns correctness. The model owns content, domain, and look.**
> Routing, auth flows, tenancy isolation, error envelopes, responsive mechanics, build
> scripts, and the publish shape are never re-derived by a model again — they ship
> pre-wired and pre-verified. The model fills in what the app IS.

## Architecture: 4 base skeletons × capability modules (not an archetype matrix)
A 12-archetypes × 6-stacks matrix would rot. Instead, **compose**:

### Base skeletons (`server/assets/skeletons/`)
| Skeleton | Stack | Serves | Exists today as |
|---|---|---|---|
| `static-site` | HTML/CSS/JS | marketing sites, landing pages, brochures | `web-app-template` (done) |
| `spa` | Vite + React (Vue/Svelte variants Phase 3) | tools, calculators, games, client-only dashboards | `react-app-template` (partial) |
| `service` | **Express single-service**: API + SQLite + built React client on ONE port | any app with a backend — the workhorse | NEW (Phase 1) — generalizes `mobile-backend-kit` |
| `api-only` | Express JSON + self-documenting index page | developer APIs, webhooks, integrations | NEW (Phase 2) |
| `expo` | Expo/expo-router (+ `add_app_backend`) | native mobile | done |

`service` is the centerpiece: one `npm install && npm run build && npm start`, API under
`/api/*` registered BEFORE the SPA fallback, relative asset paths, PORT env honored,
`NODE_ENV=production` build, graceful shutdown — every publish-pipeline requirement is a
property of the skeleton, locked by tests, never rediscovered.

### Capability modules (layered onto `service`; each = files + migrations + client pieces + verify entries)
| Module | Gives | Depends on | Covers archetypes |
|---|---|---|---|
| `auth` | JWT + bcrypt, signup/login/me, session client, seeded demo user, auth screens | — | any logged-in app |
| `orgs` | workspaces, memberships, invite codes, **withOrg isolation middleware (mergeParams-correct)**, org switcher UI | auth | multi-tenant SaaS (the TaskForge class — correct by construction) |
| `crud` | one exemplar resource end-to-end (model→route→client→list/detail/edit UI) the model CLONES for each domain entity | auth | CRUD apps, admin panels |
| `dashboard` | vendored chart lib + wrapper components + a stats endpoint pattern | — | analytics, KPI dashboards |
| `forms` | multi-step form kit + server validation + submissions table + outbox view (+ webhook/SMTP delivery when configured) | — | intake, surveys, contact |
| `uploads` | multer + `data/uploads/` convention + image thumbnailing + authed file route | auth | galleries, docs, avatars |
| `catalog` | products/categories/search + cart (session) + checkout-STUB with explicit payment-provider TODO seam | — | e-commerce until real payments |
| `booking` | resources/slots/reservations model + calendar UI + conflict rules | auth | scheduling, clinics, rentals |
| `realtime` | **SSE-first** live updates (poll fallback), WS optional behind a flag (see edge cases) | — | chat, live boards, presence |
| `cms-lite` | markdown content collection + admin editor + rendered pages | auth | blogs, docs sites |
| `jobs` | in-process cron (node-cron) + jobs table + run log view | — | digests, cleanups |
Composition rules are validated by the tool (`orgs⇒auth`, `booking⇒auth`, `cart⊂catalog`);
missing deps are auto-added, never errored.

### The tool: `scaffold_app`
`scaffold_app({ name, archetype?, modules[], stack?, look? })` →
1. Detects brownfield (non-empty repo) → **refuses to clobber**, points at the repo primer.
2. Unpacks base + modules (file merge is deterministic; module files never overlap).
3. Writes **`.arksai/CONTRACT.md`** — generated by the SCAFFOLD, not the model: response
   envelope + casing (camelCase, flat arrays), error shape `{ error: string }`, auth header,
   seed credentials, port, entity conventions. (The resume note already injects it.)
4. Writes **`.arksai/verify.json`** — the scaffold DECLARES its own verification: demo
   credentials for the gate's signed-in walker, page list, critical routes + expected
   statuses, "seed only if DB empty" marker. The gate reads the manifest when present
   instead of guessing from page text → deterministic verification for every stack,
   including API-only apps the walker can't click through.
5. Seeds demo data (idempotent — never wipes an existing DB).
6. Applies a `look` (token-file swap only — mechanics untouched, same as `create_web_app`).
The archetype router: `taskProfile` maps the brief → suggested skeleton+modules; the plan
gate shows the pick ("multi-tenant SaaS → service + auth + orgs + crud") so the user sees
the architecture before the build.

## The predictability contract (what "predictable" means, testably)
For every scaffolded app, ALWAYS true — enforced by skeleton + gate, not convention:
1. `npm install && npm run build && npm start` boots on `PORT` (default 4000) as ONE service.
2. `/api/*` routes register before the SPA fallback; all asset paths relative (path-proxy safe).
3. One response contract (camelCase, flat, `{ error }` envelope) — stated in CONTRACT.md.
4. Demo login works, is seeded idempotently, and is declared in verify.json.
5. Mobile mechanics hold at 320/390/768 (responsive layer LAST in the stylesheet; grid/flex
   shrink guards) — cascade-linted statically + walker-verified signed-in.
6. Data lives in `data/` (db + uploads); republish preserves `data/`; seed never clobbers.
7. Zero CDN dependencies; fonts and libs vendored.
8. The look is a token file; restyling never touches mechanics.

## Edge cases (the full catalog, with the decided behavior)
### Stack requests
- **Unsupported-but-runnable** (Flask/FastAPI): Phase 3 `service-py` skeleton (same contract,
  same verify.json). Until then: honest note + Node equivalent offered.
- **Unsupported-and-unrunnable** (Rails, Laravel, Spring, .NET — no runtime on the droplet):
  never fake it. Honest capability note + closest supported equivalent + the DO App Platform
  repo path (app.yaml) for users who must have that stack.
- **Next.js**: pages-router static export → treat as `spa`. App Router/RSC → refuse for
  path-proxy publish with the standing explanation; offer `service` or the DO dual-path.
- **WordPress/Shopify-alikes**: `cms-lite` / `catalog` + an honest "this is a lightweight
  equivalent, not the platform itself" line.
- **TypeScript**: JS by default (agent-authored simplicity), TS variant on explicit ask.
- **Vue/Svelte**: Phase 3 `spa` variants — same mechanics files, different component layer.
- **Monorepo / multi-service demands**: the standing single-service rule + the ask-the-user
  fork (live preview now vs multi-service DO deploy) — unchanged, now stated at scaffold time.
### Brownfield
- Non-empty repo → scaffold refuses; primer flow instead. A brownfield "add a module" ask
  (e.g. "add auth to my repo") is Phase 4: modules as guided diffs, never blind file drops.
### Module composition
- Dependency auto-add (orgs⇒auth etc.); contradictory asks (multi-tenant + "no login") →
  one clarifying line, not a broken build.
- **Realtime through the path proxy**: the client shim already rewrites WS URLs, but proxy
  UPGRADE forwarding is unverified → **SSE is the default transport** (proxy-safe, verified),
  WS behind a flag until an upgrade-forwarding test passes in the deployment proxy. The
  module's client abstracts transport so switching later is invisible to app code.
- **Uploads vs republish**: user files go in `data/uploads/`; publish must PRESERVE `data/`
  across republish (today a republish snapshots fresh — a real gap, Phase 2 publish change);
  24h preview expiry note stays honest.
- **Payments**: never real keys in scaffolds; checkout-stub with a webhook-shaped seam +
  explicit TODO; the agent must SAY payments are stubbed in the delivery message.
- **Email**: gated on SMTP config; default = in-app outbox page so the flow is demonstrable
  with zero credentials.
- **SQLite→Postgres**: `DATABASE_URL` switch in the skeleton's db layer from day one
  (publish already provisions per-app PG); migrations idempotent both ways.
### Verification
- **API-only apps**: the walker can't click — verify.json's route manifest drives curl-level
  checks (status + shape) + the self-documenting index page renders.
- **OAuth-only / no demo creds**: scaffolds ALWAYS seed a demo user; verify.json carries it.
  A model that removes the demo user fails the manifest check with a named defect.
- **Realtime verification**: manifest declares an SSE endpoint; the gate asserts it streams
  one event (bounded, 5s) — no multi-client choreography.
- **Long installs**: skeleton dependency sets are pinned and small (no Prisma by default —
  better-sqlite3 + a thin migration runner); heavy deps only arrive with the module that
  needs them.
- **RTL/Arabic** (legal dept is a first-class user): base skeletons honor `dir="rtl"` via
  logical CSS properties in the mechanics layer; a `look` can set direction.
- **Dark mode**: the existing contrast gate covers it; tokens ship both schemes or pin one.
### Publish/runtime (locked lessons)
- Root-absolute paths, API-before-fallback route order, PORT env, prod build env, npm ci
  fallback, client never prefix-detects — all skeleton properties with lock tests.
- EADDRINUSE/zombies: skeleton start script is idempotent (kills ITS OWN pidfile only —
  never a bare pkill).

## Anti-rot: the scaffold conformance suite
Scaffolds only stay "correct by construction" if the construction is tested:
1. **Unit layer**: every skeleton+module combination in a bounded matrix (each module once
   on `service`, plus `service+auth+orgs+crud` as the SaaS golden path) is assembled in a
   temp dir in tests — files merge cleanly, package.json valid, contract/verify manifests
   generated.
2. **Boot layer** (test-time, ~6 combos): install→build→boot→verify.json checks pass →
   the signed-in walker runs clean. This is the same gate users get — the scaffolds are
   permanently held to the product's own bar.
3. **Nightly canary** (QUALITY_PROGRAM item, shared): one scheduled build through the LIVE
   product using `scaffold_app`, published and gate-checked — scaffold rot pages the
   operator instead of a customer finding it.

## What the model still owns (so this doesn't become a site-builder)
Domain modeling (which entities, which fields), all copy and content, the look (via tokens,
with full creative range), extra pages/flows beyond the exemplars, and any genuinely novel
mechanics — built ON the skeleton, gated by the same checks. The scaffold is the floor,
never the ceiling.
